# Проект: AI-сервис обработки фото автозапчастей для маркетплейсов

## Контекст и цель

Я владелец каталога автозапчастей. У меня ~100 000 фото товаров в Hetzner Object Storage, которые нужно подготовить для публикации на Google Merchant, Amazon, Wildberries, Ozon. Иногда буду догружать новые партии (нечасто, вручную).

Тебе нужно построить production-ready Python-сервис, который полностью автоматически обрабатывает фото товаров под требования маркетплейсов.

## Главное правило работы

**Двигаемся строго по этапам. После каждого этапа ты останавливаешься и ждёшь моего подтверждения. Я тестирую результат на реальных фото и говорю "ок, дальше" или "нужно править".**

Цель этого правила: я должен на маленькой выборке (10-1000 фото) убедиться что всё работает корректно, и только после этого запускать на 100 000.

## Инфраструктура

- **Управляющий сервер**: VPS Hetzner Ubuntu (тут крутится оркестратор, API, БД, логи — работает постоянно)
- **GPU-обработка**: RunPod on-demand (запускаю инстанс под батч, гашу после завершения)
- **Хранилище**: Hetzner Object Storage (S3-совместимое API)
- **Интерфейс**: REST API на FastAPI (без веб-морды)

## Требования к выходу

- Формат: WebP, качество 90
- Размер: 1000×1000 px (квадрат)
- Фон: чисто белый RGB(255,255,255), без альфа-канала
- Товар: по центру, занимает 80-90% кадра по большей стороне, минимальные равные отступы
- Тени удалены
- Водяные знаки, логотипы поставщиков, телефоны, URL — удалены через inpainting
- EXIF и все метаданные очищены
- Если несколько одинаковых деталей на фото (например 2 амортизатора) — обрабатывать как единую композицию
- Если вотермарк перекрывает важную маркировку или артикул — НЕ угадывать, отправлять в review

## Структура хранилища

- **Исходники**: текущая структура папок в бакете
- **Результат**: `/up/{исходный_путь}` (та же структура внутри `/up/`)
- **На ручную проверку**: `/up/review/{категория}/{исходный_путь}` где категория = `low_confidence`, `watermark_risk`, `multiple_objects`, `processing_error`

Сделай web search и изучи **актуальные на текущий момент** SOTA модели:

6. **Изучи актуальные требования к фото товаров**: Google Merchant, Amazon, Wildberries, Ozon. Особенно — процент заполнения кадра товаром, требования к фону, размерам, формату

### Этап 4: GPU-воркер (одиночная обработка)

**Цель**: воркер берёт одну задачу из очереди, обрабатывает, загружает результат.

- Модуль `worker.py`: подключается к Redis на VPS, ждёт задач
- Загрузка моделей при старте, прогрев
- Обработка одного фото: скачать → обработать → загрузить → записать в БД
- Логирование structured JSON в stdout (RunPod собирает в свой UI) + дублирование в БД
- Обработка ошибок: 3 retry с экспоненциальным backoff, потом в `processing_error`
- Dockerfile собирается, образ публикуется на Docker Hub (или ghcr.io)

**🛑 СТОП. Я запускаю воркер на RunPod. Через API VPS кидаю в очередь 10 фото. Смотрю что отрабатывает корректно, результаты в бакете, логи в БД.**

### Этап 5: API и оркестратор

**Цель**: я могу через HTTP API создать задачу на обработку и следить за прогрессом.

Endpoints:
```
POST /jobs              — создать задачу: либо префикс пути в бакете, либо список путей
GET  /jobs              — список задач
GET  /jobs/{id}         — детали: total/processed/failed/in_review/processing_speed/ETA
GET  /jobs/{id}/log     — логи задачи (с пагинацией)
POST /jobs/{id}/stop    — остановить (текущие фото докрутить, новые не брать)
POST /jobs/{id}/resume  — возобновить
POST /reprocess         — список путей, игнор кеша
GET  /stats             — общая статистика
GET  /stats/cost        — реальная стоимость обработанного (на основе фактического времени и цены RunPod из конфига)
GET  /health            — health check
```

- Защита: API-ключ из переменной окружения, передаётся в header
- Celery (или что выбрал) — связка очереди с воркерами
- ETA: на основе скользящего среднего скорости

**🛑 СТОП. Тестирую API через curl/Postman. Создаю задачу на 100 фото из моего бакета. Слежу за прогрессом, смотрю результат.**

## Нефункциональные требования

- **Идемпотентность**: повторный запуск не переобрабатывает готовое (проверка по хэшу)
- **Устойчивость**: воркер падает → задача возвращается в очередь, retry × 3 с backoff
- **Логирование**: structlog или loguru, structured JSON, ротация
- **Конфиг**: всё через `.env` + `config.yaml`, никакого хардкода
- **Тесты**: pytest на ключевую логику (композиция, центрирование, confidence, расчёт стоимости) + интеграционный тест на 10 фото
- **Документация**: подробный README + отдельный `RUNBOOK.md` (как запустить полный прогон, что делать если упало)
- **Безопасность**: API-ключ, никаких credentials в коде, secrets через env
